## Delivered Behavior

- Signup passes cfg.Auth.BCryptCost to model.HashPasswordWithCost, so new user hashes encode the configured work factor rather than always using bcrypt.DefaultCost. Hatmax's existing default of 12 now takes effect.
- The explicit-cost primitive accepts bcrypt.MinCost through bcrypt.MaxCost (4 through 31). Invalid values return a wrapped bcrypt.InvalidCostError without a default-cost fallback. Invalid costs and bcrypt password-length failures return no hash and prevent user creation through signup.
- model.HashPassword keeps its original non-variadic signature and bcrypt.DefaultCost behavior (10). ComparePassword, Signin, session behavior, and stored hashes are unchanged. A different future-signup cost does not invalidate an existing hash or trigger automatic rehashing.
- Authentication, model, and configuration references, Godoc, and Unreleased describe the effective policy and the standalone helper's compatibility.

## Contracts and Ownership

Auth owns the signup policy through the existing configuration field; model owns bcrypt hashing and comparison. HashPasswordWithCost is the explicit-cost primitive, and HashPassword delegates with bcrypt.DefaultCost. No configuration key, dependency, hash format, persistence contract, constructor, migration, rehash policy, or password-comparison algorithm was changed.

The explicit range check prevents [bcrypt's below-minimum default fallback](https://pkg.go.dev/golang.org/x/crypto/bcrypt#GenerateFromPassword). The local x/crypto v0.57.0 source was checked: hashing embeds the cost, and comparison reads the cost from the stored hash. Existing Config.Validate bounds and error text remain unchanged.

Honoring higher configured costs increases hashing work. The accepted range remains the existing 4 through 31; no deployment-specific cost recommendation, new execution deadline, or admission policy is introduced. Tests generate hashes only at practical costs 4, 6, 10, and 12, not the expensive upper boundary.

## Validation

All Go checks used Go 1.26.7. Auth behavior tests use the existing in-memory Queries fake with the real bcrypt implementation. Full repository database tests used an isolated native PostgreSQL 18.6 cluster on loopback, stopped after validation. This is local evidence, not production authentication acceptance or CI against PostgreSQL 16.

- Before the fix, `go test ./auth -run '^(TestSignupCost|TestSignupHashFailure)$' -count=1` failed: configured costs 4, 6, and 12 all produced cost 10, and invalid costs still created users when configuration validation was bypassed.
- `make check`: passed licensing, formatting, vet, all tests, coverage, and strict lint. Total coverage: 81.5%; auth: 92.3%; model: 97.1%.
- `make docs-check`: passed.
- `go test -race ./auth ./model -count=1`: passed.
- `go test ./auth ./model -run '^(TestSignupCost|TestSignupHashFailure|TestHashCost|TestHashCompatibility)$' -count=20`: passed all 20 repetitions.
- `git diff --check`: passed.

Named cases verify encoded costs, persisted hash content, correct and incorrect password comparison, successful session creation after changing the signup policy, invalid-cost rejection with unchanged configuration validation, no persisted user on hashing failure, negative/zero/out-of-range helper costs, empty passwords at the primitive boundary, the 72/73-byte length boundary, and the original helper's function type and default cost.

## Boundary

Only F18 is corrected. Existing hashes are not rewritten. Password reset/change workflows, cancellation during bcrypt CPU work, auth persistence adapters, random-password generation, session policy, and other review findings remain unchanged.
