# Generate a Feature

This chapter uses the Hatmax generator to add one server-rendered feature to
an existing application. You inspect the complete plan before deciding whether
Hatmax may change the project.

## Before You Begin

Use a Git checkout of a Go application that depends on Hatmax `v0.5.x`. The
project must have a `go.mod`; a `Makefile` and `sqlc.yaml` let the generator run
the project's own formatting, generation, and validation commands.

Install the Hatmax command:

```sh
go install hatmax.adrianpk.com/cmd/hatmax@v0.5.0
```

Install and sign in to the Codex CLI by following the
[official Codex CLI documentation](https://learn.chatgpt.com/docs/codex/cli).
Hatmax uses its managed App Server and reuses the resident daemon between
requests.

Commit or otherwise preserve the current project state before continuing.

## Request the Feature

From the application root, run:

```sh
hatmax generate "Create a property feature with a required name."
```

Hatmax inspects the project and asks Codex to map the request to the bounded
Hatmax intent. If a required product choice is missing, answer each
clarification prompt. Codex interprets the request; it does not choose the
project edits.

## Inspect and Approve the Plan

The command prints a typed plan before it changes any file. Check the intent,
feature, capabilities, affected surfaces, allowed effects, validation
commands, and documentation mode.

Enter `y` or `yes` only when the plan matches the request:

```text
Approve plan <digest>? [y/N]: y
```

Any other answer cancels the run without applying the plan. If the project
changes after planning, Hatmax rejects the stale approval instead of applying
it to a different project state.

## Inspect the Result

After approval, Hatmax applies the canonical Book renderers, checks the result
against the sealed plan, and runs the applicable commands discovered in the
project. The final report lists changed surfaces, conformance diagnostics, and
command evidence.

Review the Git diff and run the application-specific acceptance path. A
completed run establishes that the generated changes passed the discovered
commands; it does not replace product-level review.

Documentation is not generated by default. Ask for it explicitly in the
request when the change should also create or update a boxed Diataxis page.

## Recover from a Rejected Run

- Missing answers cancel clarification without changing the project.
- An unsupported request stops outside the Hatmax Book instead of selecting a
  different framework or pattern.
- A stale plan requires running the request again against the current project.
- A renderer, conformance, or project-command failure is reported as an
  execution failure with the available evidence.

See [Generator](../../reference/generator/index.md) for supported operations,
runtime behavior, and stable exit statuses.

## Verify the Result

This chapter is complete when the plan was explicitly approved, the command
reported completion, and the generated feature passes the application's own
acceptance check.
